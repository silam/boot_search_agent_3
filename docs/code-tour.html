Boot Search Agent, file by file

Every code block on this page is pulled from the repo as it is, with the file and line it starts on. Read top to bottom and you follow one search from the raw catalog to the answer on screen. Each section ends with a line you can say out loud in the interview.

00 · ARCHITECTUREwhole system

Two paths: indexing offline, searching online

The top lane runs once (or whenever the catalog changes): it cleans the catalog, cuts it into chunks, embeds them and loads Qdrant plus the BM25 index. The middle lane runs on every search: the Streamlit UI calls FastAPI, FastAPI checks the cache and hands the request to the LangGraph agent, and the agent calls the retrieval tools in parallel and, if a key is set, Claude.

"Indexing and serving are separate paths. Indexing is a batch job that can be re-run safely; serving is a stateless API that any replica can run, which is what lets it deploy to Vercel or scale on Kubernetes."

01 · CONFIG & MODELSapp/core/

Contracts first: one model per idea, settings from the environment

Every layer speaks in the same Pydantic types: Boot (a clean product), Chunk (a piece of text that points back to a boot), Filters (structured constraints), RetrievedItem (one retriever's hit) and SearchResult (a fused, final hit). Filters is the one with behaviour: it is the single definition of "does this boot match", used by BM25, by the final safety net, and in the eval.

  • safety_toe="any" means "needs some safety toe", so "safety boots" doesn't have to guess steel or composite.
  • is_empty() lets the Qdrant layer skip building a filter at all.
  • The validator lowercases colours at the boundary, so the rest of the code never handles "Black" vs "black".

Settings: one image, many environments

Everything below is read from environment variables or .env. Swapping embedded Qdrant for Qdrant Cloud, or the lite embedder for CLIP, is a variable change, not a code change.

Composition root: build once, heal on startup

get_engine() is cached with lru_cache, so the models and index are built once per process. It re-runs the ETL if the raw data or chunking settings changed, and re-indexes if Qdrant is empty, which is what makes a brand-new container (Vercel cold start, new Kubernetes pod) able to start on its own.

Say it in the interview

"Validation happens at the edges, in ingestion and in the API schemas, so the inner layers can trust their inputs. And Filters.matches is the single source of truth for what a match is."

02 · INGESTION (ETL)app/ingestion/ · scripts/ingest.py

Load, clean, chunk, embed: and keep a receipt

Extract: one interface, any source

Each loader has a single load() method returning raw dicts. A new source (a supplier API, an S3 bucket, a Kafka topic) is one new class.

Transform: clean, validate, reject with a reason

  • The sample catalog has two planted bad rows: a duplicated, shouting, HTML-polluted description and a record with no name. Both end up in rejected.json with a reason, and the clean count (48) is a data-quality number you could alert on.
  • Boot(**normalise_record(raw)) is where Pydantic validation happens. Bad prices, unknown categories and empty names fail here, not deep inside retrieval.

Chunking: by section, then recursively by size

Each boot becomes three kinds of chunk: a profile (structured attributes written as a sentence, including the SKU), the description, and the reviews. Inside a section, long text is split on the coarsest separator that exists (paragraph, line, sentence, clause, word) with a 60-character overlap, which is the same idea as LangChain's RecursiveCharacterTextSplitter.

  • Putting the SKU in the profile chunk is what makes BOOT-042 findable by BM25. Before that fix, the SKU search returned unrelated rain boots.
  • Non-waterproof boots say "water-resistant only" rather than "not waterproof", because BM25 would otherwise match the word "waterproof" in a negative sentence.

Load: embed in batches, upsert idempotently, detect staleness

Say it in the interview

"Garbage in, garbage out is worse in RAG, because a dirty description becomes a dirty vector and dirty LLM context. So the pipeline validates, rejects with reasons, chunks by section so I can show evidence, and records lineage so I know when to re-index."

03 · EMBEDDINGSapp/embeddings/

One interface, two backends

Retrieval depends on TextEmbedder and ImageEmbedder, never on a model. That is the Strategy pattern, and it buys three things: tests and CI run without PyTorch, a small serverless image is possible, and swapping in a hosted embedding API later touches one file.

BackendText vectorsImage vectorsText → imageUsed for
liteHashing trick: words, bigrams, char trigrams → 768-dColour histogram + 16×16 silhouette → 472-dNoTests, CI, Vercel
clipsentence-transformers MiniLM-L6 → 384-dOpenCLIP ViT-B/32 → 512-dYes (shared space)Real semantic quality
  • Every vector is L2-normalised, so a dot product equals cosine similarity.
  • embed_text_for_image exists only on CLIP-style models, because text and image vectors are comparable only when one model produced both.

The lite text embedder: lexical, cheap, deterministic

Character trigrams give typo tolerance ("waterprof" still overlaps "waterproof"). It is lexical, not semantic: "cowboy" will not match "western". That is stated plainly in the README, and it's why the eval shows the vector-only score lowest with this backend.

The CLIP backend: cross-modal search

CLIP was trained on image captions, so the query is phrased like one ("a product photo of …"). MiniLM handles product text; CLIP's text tower is used only to search the image space, because it is capped at 77 tokens.

Say it in the interview

"I use each model for what it was trained on: a sentence model for product copy, CLIP for images and for text-to-image. And the interface means CI never needs a GPU or a model download."

04 · VECTOR DATABASEapp/retrieval/qdrant_store.py

Qdrant: payload filters inside the search, not after it

Two collections: boot_text_chunks (one point per chunk) and boot_images (one point per photo, so 8–10 points per boot). Every point carries the product attributes as a payload, with payload indexes on the filter fields. The important choice is where filtering happens.

  • Search runs over chunks, then keeps the MAX score per boot. A boot whose review says "kept my feet dry all day" can win on that one chunk, and that chunk becomes the evidence shown in the UI.
  • The search over-fetches chunks (k × 3 in the engine) because aggregation to boots shrinks the list.

If the embedding dimension changes (lite 768-d → MiniLM 384-d), old vectors are meaningless, so the collection is dropped and rebuilt. Point ids are uuid5(chunk_id), so running ingestion twice overwrites instead of duplicating.

Say it in the interview

"I filter inside the HNSW search, because post-filtering a top-k can leave you with nothing. HNSW is an approximate nearest-neighbour graph; m, ef_construct and hnsw_ef trade recall for latency."

04b · MANY PHOTOS PER BOOTcatalog.json · pipeline.py · qdrant_store.py · search_engine.py

One vector per photo, grouped by boot, scored by the best photo

Every boot has a gallery of 8–10 photos: side, mirrored side, three-quarter, front, back, top, sole, a toe close-up, and sometimes a heel close-up and an on-the-floor shot. Each photo is embedded and stored as its own Qdrant point carrying the boot's id. A search groups those points by boot and gives each boot the score of its best-matching photo. That is MaxSim.

The catalog record

The first photo is the primary one (thumbnails, the old /image endpoint). The view name travels with every photo.

Cleaning the gallery

  • Accepts a list of {path, view} objects, plain paths, a "a.png|b.png" CSV cell, or the old single image field.
  • Blocks absolute paths and .. so a bad catalog row can't make the API serve files outside data/raw/.
  • Missing files are dropped and reported in rejected.json with kind: "image"; the boot itself stays.

Indexing every photo

The point id is uuid5("img:{boot}:{path}"), so re-running ingestion overwrites. The manifest now also stores a hash over every photo's bytes, so a re-shot photo triggers re-indexing even when catalog.json is unchanged.

Grouped search

  • limit counts boots, not photos. group_size=3 brings back each boot's best three photos for the optional mean_top3 scoring.
  • Product filters (waterproof, price, …) are in every photo's payload, so they still run inside the HNSW search.
  • views and exclude_paths exist for the evaluation: "search only side photos" simulates the old one-photo index, and excluding the query photo makes a leave-one-out test possible.

Several query photos at once

score(boot) = meanq ∈ query photos  maxp ∈ boot photos  cos(q, p)

This is symmetric MaxSim (Chamfer similarity) between two sets of photos. Each query photo only needs to match the catalog view taken from the same angle, but the boot has to look right from every angle the shopper showed. The unit test checks that a boot good from both angles beats a boot that is great from one and absent from the other.

Does it help? Measured on held-out photos

The generator also writes 192 "shopper photos": new shots of a boot from one of its angles with stronger rotation, scale, lighting and background changes. They are never indexed.

The gain is largest for angles a single side photo can't cover: sole (MRR 0.71 → 0.83), top (0.37 → 0.57) and toe close-ups (0.83 → 0.94). A second test removes the query's own angle from the target boot. There one canonical photo wins (MRR 0.75 vs 0.50), because other boots' photos from that angle compete. A CI gate requires every-photo MaxSim to beat one photo per boot on the shopper set.

Say it in the interview

"Each photo is its own vector, Qdrant groups hits by product, and the product scores by its best photo. That lets a sole photo match the sole view and tells the shopper which photo matched. I measured it on held-out photos, product@1 went from 0.67 to 0.77, and I found where it's weaker: when the catalog lacks the query's angle, which points to a view-invariant embedder or blending in a per-product centroid."

05 · KEYWORD SEARCHapp/retrieval/bm25_index.py

BM25: the part dense vectors are bad at

score(q, d) = Σt∈q IDF(t) · tf(t,d)·(k₁+1) / ( tf(t,d) + k₁·(1 − b + b·|d|/avgdl) )   ·   k₁ = 1.5, b = 0.75
  • IDF: rare words ("kiltie", "Vibram") count far more than common ones ("leather").
  • k₁: term-frequency saturation, so the fifth "waterproof" in a chunk adds little.
  • b: length normalisation, so a long chunk doesn't win just by being long.

The same tokenize() must run on documents and queries, or "laces" will never match "lace". Hyphenated words are kept whole and split ("slip-resistant", "slip", "resistant"), and words like "boot", "want" and "show" are stopwords because they appear everywhere.

Say it in the interview

"Embeddings miss exact tokens: SKUs, model names, numbers, jargon like 'kiltie'. BM25 nails those and explains itself. At millions of documents I'd move it into Qdrant sparse vectors or OpenSearch so both run in one engine."

06 · FUSIONapp/retrieval/fusion.py

Reciprocal Rank Fusion: combine ranks, not scores

RRF(d) = Σr wr / (k + rankr(d))   ·   k = 60, rank starts at 1

BM25 scores are unbounded (0 to 30+), cosine sits in [−1, 1], and image similarity has its own spread. Adding them needs fragile normalisation. RRF ignores the scores and uses only positions, so a boot that several retrievers agree on rises to the top.

Worked example

BM25 returns A, B, C. The vector search returns B, D, A. Both weights are 1.

B wins even though BM25 ranked A first, because both retrievers placed B near the top. Weights shift this: for a SKU lookup the agent sets keyword: 2.0, and when a photo is uploaded with text it sets image: 1.5. The unit test test_rrf_weights checks exactly that.

Say it in the interview

"RRF is scale-free and needs no training, and k = 60 is the value from the original paper. The next step would be a cross-encoder re-ranker over the fused top 50: better quality, more latency."

07 · SEARCH ENGINEapp/retrieval/search_engine.py

The agent's tools, run in parallel

SearchEngine exposes four tools: keyword (BM25), semantic (text vectors), image (image vectors) and text_to_image (CLIP only). The agent hands it a RetrievalPlan: which tools, what weights, which filters. retrieve() runs the chosen tools on a thread pool and times each one; fuse() applies RRF and a final filter check.

  • Threads, not asyncio: embedding and local Qdrant are blocking calls, and a pool of 4 runs them side by side.
  • plan.filters.matches(boot) in fuse() is a safety net for every retriever, so a filter can never be silently dropped by one path.
  • Photo + "but waterproof": image search finds the look, BM25 and vectors find the words, the waterproof filter is enforced on all three, and RRF rewards boots in more than one list.
08 · LANGGRAPH AGENTapp/agent/graph.py

A bounded state machine that plans, retries and checks itself

Each box is a Python method that takes the shared AgentState and returns the fields it changed. LangGraph merges the updates and follows the edges. Two edges are conditional: guard_input can end the run early, and reflect can send the run back to retrieve.

Wiring the graph

This is the whole control flow in 18 lines. Compare it with a free-form ReAct loop: here the number of steps is bounded, each node is a plain method you can unit-test, and the trace is predictable.

The shared state

understand: LLM first, rules as the safety net

Claude is asked for strict JSON. If there's no key, the call fails, the JSON doesn't parse, or the values break the Filters schema, the rule-based parse stays in place. The UI's explicit filters are merged on top and always win.

reflect: the self-correction loop

  • Filters are relaxed in a fixed order, least important first: colour, price, waterproof, safety toe, category.
  • Anything the user set in the UI is in user_set and is never relaxed. The test test_user_filters_are_never_relaxed pins this.
  • The relaxed fields go back to the UI, which tells the shopper "No exact match — the agent relaxed: max_price".

Say it in the interview

"It's agentic because it chooses its tools from the query and re-plans when results are empty. I used a graph instead of an open ReAct loop because I want bounded cost and latency and a testable, explainable trace; the LLM does language work, not control flow."

09 · PROMPTS & LLMapp/agent/prompts.py · app/agent/llm.py

Prompts that produce parseable, grounded output

Two prompts. The query-understanding prompt returns JSON matching a schema, with few-shot examples for synonyms, SKUs and vague queries. The answer prompt comes in two variants for A/B testing and is only ever given the retrieved products.

  • Catalog text, including customer reviews, sits inside <catalog> tags and the prompt says it is data. That is the defence against indirect prompt injection planted in a review.
  • Context is compact: one line per product, top 5 only, evidence trimmed to 200 characters. Fewer tokens means lower cost and less room to drift.
  • PROMPT_VERSION is logged in every trace and is part of the cache key, so a prompt change never serves stale answers.

The client: timeouts, retries, cost, and never crashing

Any exception returns None and records the error type, which becomes the llm_errors_total metric. Token counts are turned into dollars with prices from settings, so cost shows up per request and in Grafana.

Say it in the interview

"The model is a dependency that can fail, so every call has a timeout, retries and a fallback. A small fast model does extraction; the answer prompt only sees retrieved products, and the output is verified before anyone sees it."

10 · GUARDRAILSapp/guardrails/

Checks before the LLM and after it

Input guard

  • Length limit and empty-request check.
  • Prompt-injection score from weighted patterns; block at 0.8.
  • PII redaction: email, phone, SSN, Luhn-checked card numbers.
  • Image checks: size, format, decompression-bomb limit.

Output guard

  • Every SKU in the answer must be in the results.
  • Every product name must be a shown product, matched on word boundaries after removing shown names (so "Cascade II" doesn't flag "Cascade").
  • Every cents-precise price must be a shown price.
  • Fail → replace with the template answer and count it.

The substring rule came from testing: the template answer named "Granite Forge Cascade II", and the first version of the check flagged the unshown "Granite Forge Cascade". The fix removes shown names first, and a regression test now covers it.

Say it in the interview

"Regex catches the obvious injections cheaply, but the real protection is architectural: the LLM has no tools that can do damage, retrieved text is marked as data, and the answer is verified. PII is removed before anything is logged, cached or sent to a third party."

11 · FASTAPIapp/api/main.py

One search request, end to end

Startup and middleware

  • Models and the index load once in lifespan, never per request.
  • The middleware labels metrics with the route template (/search), not the raw URL, so Prometheus label cardinality stays small.
  • Every route is mounted twice, at / and under /api, so the same container works behind Vercel's /api/* rewrite.

Security dependency and the A/B split

The heart of /search: cache, then agent

The cache key includes everything that changes the answer: query, mode, filters, top_k, prompt variant, a hash of the image bytes, the prompt version and the catalog size. The endpoint is a plain def on purpose, so FastAPI runs the blocking agent in its thread pool instead of stalling the event loop.

Say it in the interview

"The API is stateless. Heavy objects load once at startup, every request gets an id that's in every log line, and the metrics I watch are quality signals: zero-result rate, grounding failures, guardrail blocks and cost, not just latency."

12 · CACHE & FEEDBACKapp/cache/ · app/storage/

Cheap repeats, and a loop that makes search better

Redis is shared across replicas and has TTL eviction built in. If it isn't reachable, an in-process TTL dict takes over, so local development needs nothing running. Invalidation works by versioning the key, not by deleting entries.

The continuous improvement loop

GET /feedback/stats groups the same tables by prompt variant and returns the thumbs-up rate, average latency and total cost per variant: that is the online A/B test result.

13 · STREAMLIT UIui/streamlit_app.py

A thin client that explains itself

The UI holds no model and no index. It builds a payload, posts it, and renders what comes back, which is why it can deploy and fail independently of the API. The design choices are about trust: show which retriever found each boot and the text that matched, say which filters were relaxed, let the user override the agent, and collect feedback.

  • md() exists because Streamlit markdown renders $159.99 … $189.99 as LaTeX. The first screenshot showed prices turning into math; this is the fix.
  • esc() HTML-escapes product names and review text before they go into unsafe_allow_html markup, which prevents stored XSS from catalog data.
  • session_id is a random id kept in session state; the API hashes it to pick prompt variant A or B.

The quality gate in CI

Testing the LLM path without an LLM

A fake client returns canned JSON for understanding and a canned answer for generation. That makes the LLM path deterministic, fast and free to test, including the failure case where the model invents a product.

Say it in the interview

"Retrieval quality caps answer quality, so I evaluate retrieval on its own with P@5, recall, MRR and nDCG, and gate the build on it. Generation is scored offline with an LLM judge or Ragas, and online with thumbs-up rate per prompt variant."

15 · DEPLOYMENTvercel.json · docker/ · docker-compose.yml · k8s/

Same images, three places to run them

Vercel: two container services in one project

  • Vercel sends traffic to port 80 unless PORT is set, so the container listens on ${PORT:-80}.
  • The ETL runs at build time, so the image ships with processed data and a cold start only has to index.
  • Streamlit needs a WebSocket. Vercel supports them (public beta), but a connection closes at the function's maximum duration (300 s on Hobby) and Streamlit reconnects.

Docker Compose: the full stack locally

Kubernetes: what production looks like

Qdrant runs as a StatefulSet with a persistent volume, ingestion is a Job (a CronJob for nightly refreshes), the API scales 2→10 pods on CPU with an HPA, and rolling updates use maxUnavailable: 0 for zero-downtime deploys. Liveness hits /health; readiness hits /ready, which only answers once the index is loaded.
